## 한 줄 판정

**방향은 맞고, 조건부 진행이다.** 다만 「높음」 5개는 PRD 를 고친 다음에 [5] 분해로 넘어가야 한다. 다섯 다 코드나 실험 데이터로 확인했다. 모델을 둘 자리, 다시 들어오는 retired 단어 8개, 출력 순서와 id 묶기, 조약돌 이름 73개 충돌, 음력 계산이 갈라지는 문제다.

## 아키텍처 의견

- **판정(judge)은 그대로 두고 고르는 방법만 바꾸는 구조가 좋다.** 「거짓말 안 하기」가 모델 바깥에 남는다. 학생이 후보 밖 단어를 낼 수 없다는 점(분류기에 마스크를 씌움, `student.py:67`)도 맞다.
- **인코더와 고르기 층을 Core ML 파일 하나로 묶지 말 것.** 인코더(TinyCLIP int8)만 Core ML 로 두고, 고르기 층은 `float16 행렬 + 단어 id 목록 + mean/std` 를 담은 작은 파일로 두자. 점수는 Swift(Accelerate)로 512×1,800 내적을 한 번 하면 되고 1ms 도 안 걸린다. 그러면 단어 목록이 바뀔 때 Core ML 을 다시 변환할 필요가 없고, 「점수 i번 = 어느 단어인가」가 파일 안에 그대로 적힌다(H3).
- **Shared 쪽에는 주입 지점만 둔다.** 지금 `WordAssist.choose`(`WordChoice.swift:79-93`)처럼 앱 타깃이 채우는 클로저나 프로토콜이 확장 문제(H1)와 테스트 문제를 같이 푼다. `WordAssist` 를 빼더라도 이 지점은 `WordScorer` 라는 이름으로 남기자.
- 모델은 `actor` 하나에서 한 번만 불러오고, 앱을 시작할 때 백그라운드에서 미리 데운다.

## 위험·빈틈

### 높음

- **H1. 모델을 `Shared/` 에 두면 세 타깃에 복사된다.** `project.yml:21,68,94` 를 보면 `Shared` 가 앱·잠금화면 캡처 확장·위젯에 모두 소스로 들어간다. 빼는 것은 글꼴뿐이라 `Shared/Word/` 의 모델(≈10MB)과 `words.json` 이 확장마다 들어간다. 그러면 앱 크기 ≤25MB 를 넘고, 확장이 실수로 모델을 불러오면 확장 메모리 한도에 걸린다. 게다가 PRD 의 「0.2초를 넘으면 담을 때 미리 고른다」는 금지 영역(`Capture/**`)이고, 담는 일은 잠금화면 확장에서 일어난다.
  → `WordModel.swift` 와 모델 파일은 `ColorMoments/App/` (앱 타깃만)에 둔다. Allowed Touch Surface 도 고친다. 미리 고르는 일은 「앱이 담긴 사진을 받을 때(앱 프로세스)」로 바꾼다.
- **H2. 예전에 뺀(retired) 단어 8개가 새 단어로 다시 들어온다.** `words-expanded-v5.json` 에 개밥바라기·샛별·달무리·비설거지·단잠·달맞이·손때·말벗이 `new: true` 로 있다. 이 단어들을 로마자로 바꾸면 지금 `words.json` 의 `retired` 에 있는 id(`danjam`, `saetbyeol`…)와 똑같아진다. 그러면 `contradicted` 가 retired 를 먼저 보기 때문에(`WordPicker.swift:152`) 새 기기에서도 붙자마자 가려진다. 다른 id 를 주더라도, 옛 기기는 자기 retired 목록으로 같은 id 를 지우고 iCloud 로 서로 지우기를 되풀이한다(같은 파일 24-25줄의 경고와 같은 종류다).
  → 새 id 는 **이제까지 나간 모든 버전의 id 와 retired 목록에 없는 것**이어야 한다. 테스트로 막는다. 이 단어들은 「사진으로 확인할 수 없어」 뺀 것이었으니, 다시 넣을지 자체를 Tabber 가 정해야 한다.
- **H3. 고르기 층의 출력 차원이 목록 순서에 묶여 있다.** `student.py:26` 에서 `index = {id: i}` 를 목록 순서대로 만들고, 63줄 `Linear(…, len(words))` 가 그 순서를 따른다. 단어를 하나 더하거나 빼거나 순서만 바뀌어도, 오류 없이 엉뚱한 단어가 붙는다.
  → 고르기 층 파일에 id 목록(또는 해시)과 목록 버전을 같이 싣는다. 불러올 때 `words.json` 과 다르면 규칙으로 넘어가고, 번들 파일끼리 맞는지는 단위 테스트로 확인한다.
- **H4. 새 단어 73개가 조약돌 이름과 겹친다.** 노을·햇살·안개·무지개·진달래 등이다. 지금 `WordListTests.testNoWordCollidesWithAPebbleName`(`WordListTests.swift:25-41`)이 깨진다. PRD 에는 이 얘기가 없다.
  → 조약돌 이름과 사진 단어를 나눈 규칙을 지킬지 풀지 정해야 한다(Tabber).
- **H5. 음력을 공방과 앱이 다르게 계산한다.** 공방 `cond.py:8,78-84` 는 `korean_lunar_calendar`(한국 천문연 기준)를 쓰고, PRD 는 `Calendar(.chinese)` 다. 중국 음력은 동경 120° 기준이라, 합삭이 한국 시각 0~1시 사이면 달의 첫날이 하루 어긋난다. 윤달 처리도 다르다. PRD 는 윤달을 맞지 않는 것으로 보는데, `cond.py:80` 은 `[5:10]` 로 잘라서 윤5월 5일도 「05-05」로 본다. `judge` 는 단어를 지울 때도 쓰이므로(`WordPicker.swift:24-25`) 버전이나 기기마다 결과가 다르면 서로 지우기가 된다.
  → 공방에서 `korean_lunar_calendar` 로 「2000~2060년, 음력 날짜 19개 + 12-last → 양력 날짜」 표를 만들어 번들에 넣고, 앱과 공방이 같은 표를 읽는다. 표는 고정한다(넓히기 금지 규칙과 같다).

### 중간

- **M1. 스레드와 첫 로드.** SwiftUI `View` 는 MainActor 라서 `pickWord`(`DayPhotoView.swift:361-377`) 안의 동기 호출은 메인 스레드에서 돈다. 업데이트 뒤 첫 실행 때 `MLModel` 로드(ANE 컴파일)는 수백 ms~수 초 걸릴 수 있다.
  → 로드·예측은 actor 안에서만 한다. 0.2초 기준은 「데워진 상태」와 「설치 뒤 첫 장」으로 나눠 잰다. **느린 것과 실패한 것을 구분해야 한다.** 단어는 한 번 붙으면 안 바뀌기 때문에, 시간 제한에 걸려 규칙으로 떨어지면 그 사진은 영원히 규칙 단어로 남는다.
- **M2. Vision 라벨은 계속 필요하다.** 날씨 짐작(`PhotoContext.swift:54`)과 붙은 단어 판정(`WordPicker.swift:174`, 저장된 `labels`)이 라벨을 쓴다. 라벨을 안 만들면 판정이 바뀐다. 그러니 분류 + 같은 장면 비교(`DayPhotoView.swift:338-350`)는 계속 돌아야 하고, 지연 예산은 「라벨 + 인코더」로 잡아야 한다. PRD 흐름도에는 라벨 단계가 빠져 있다.
- **M3. 최근 단어 피하기가 정해지지 않았다.** 지금은 가까운 14장의 단어와 두 번 넘게 버린 단어를 피한다(`DayPhotoView.swift:365`, `DayStore.swift:396-405`). 학생 1등에도 이것을 적용할지 PRD 에 없다. 「한 단어 4번 이하」 기준을 잴 때도 공방 평가가 앱과 같은 방식으로 최근 단어를 흉내 내야 숫자가 맞는다.
- **M4. ↻ 흐름.**
  - 지금 `reject` 는 저장된 라벨만으로 다시 고른다(`:397-400`). 학생으로 2등을 고르려면 사진을 다시 인코딩해야 한다.
  - **사진 값을 `Moment` 에 캐시하면 iCloud 로 나간다** — 첫 약속을 어긴다. 메모리 캐시만 쓴다고 PRD 에 적어 두자.
  - `hasAlternative`(`:390-395`)는 규칙 후보를 기준으로 하고 body 가 그려질 때마다 돈다. 「판정을 통과한 후보가 2개 이상」으로 바꾼다.
  - 「2등」은 「지금 단어·버린 말·쉬는 말을 뺀 1등」으로 정의하자. 처음 붙은 단어가 규칙이나 옛 버전이 고른 것일 수 있기 때문이다.
- **M5. 쉬게 하기와 대비책이 부딪힌다.** 이름표 64개가 쉬면, 대상(subjects)에 기대는 규칙 대비책은 거의 다 때 말로 빠진다. 새 단어 1,622개에는 `subjects` 가 없다. 쉬는 말을 빼는 필터는 `WordPicker` 한 곳에만 두고(`hasAlternative`·`reject`·리포트가 모두 거치게), `contradicted` 는 `rest` 를 보지 않는다는 것을 테스트로 고정한다.
- **M6. 맥과 iPhone 의 사진 값.** `embed.py` 는 HF 전처리(PIL 바이큐빅)를 쓴다. Core ML 이미지 입력은 크기가 고정이라 「전처리를 모델 안에」는 정규화까지만 들어간다. 리사이즈·자르기는 앱의 Swift 함수 하나(600px 썸네일 → 224)로 만들고, 공방 추출 도구가 그 함수를 그대로 컴파일하게 한다(지금 `extract/` 와 같은 방식). 검증은 「코사인 5장」 대신 **94장 1등 일치율 ≥ 95%** 로 하고, compute units 는 고정한다. `student.py:76` 의 mean/std 도 고르기 층과 함께 실어야 한다.
- **M7. id 규칙.** `testIDsAreUniqueAndStable` 은 `^[a-z]+$`(`WordListTests.swift:16`)인데, 「겹치면 숫자」를 붙이면 이 테스트가 깨진다. 로마자 id 는 한 번 만들고 `words.json` 에 고정해야 한다. 공방이 다시 생성하면 id 가 바뀔 수 있다.
- **M8. 명조 서브셋.** 지금 242자이고 v5 단어를 넣으면 590자(+348)가 된다. 크기는 82KB 에서 약 200KB 로 늘 것으로 보여, `testSubsetStaysSmall` 의 100KB 상한(`FontSubsetTests.swift:62`)과 README 의 「200자 미만」이 깨진다. 상한은 근거를 적고 올린다. 이 글꼴과 `words.json`(약 330KB)도 확장에 복사된다(H1 과 같은 원인). 확장에서도 빼자.

## 빠진 테스트

1. 번들의 고르기 층 id 목록이 `words.json` 과 같은지, 다르면 규칙으로 넘어가는지.
2. 새 id 가 지난 모든 버전의 id·retired 와 겹치지 않는지(옛 `words.json` 을 픽스처로).
3. 기존 170개 조건이 좁아지기만 했는지 — 옛 픽스처와 필드별로 비교한다. `lunar`·`solar` 를 새로 붙여도 좁히기다.
4. 음력 표: 설날·한가위·12-last(섣달이 29일인 해와 30일인 해), 윤달이 든 해, 한국과 중국 음력이 갈리는 날. 그리고 `cond.py` 와 Swift `judge` 가 같은 결과를 내는지(사진 3,000장 판정 비교).
5. 가짜 `WordScorer` 를 끼워서 확인할 것: 모델 없음 → 규칙, 예외 → 규칙, 늦음 → 정한 정책대로, 1등이 쉬는 말이나 버린 말이면 건너뜀.
6. ↻: 2등이 지금 단어를 빼고 고르는지, 후보가 1개면 ↻ 가 숨는지.
7. 쉬는 말: 후보에서는 빠지고 이미 붙은 것은 남는지(`standingWord`).
8. 확장 번들에 모델 파일이 없는지(H1 의 회귀 방지 — 지금의 `GowunDodum-Mini` 검사처럼).
