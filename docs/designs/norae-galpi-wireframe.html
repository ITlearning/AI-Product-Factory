재생은 ⑥에서만 — 유튜브 약관이 정한 형태

처음 설계는 재생 중인 카드가 화면을 벗어나면 하단 미니 플레이어로 줄어들어 따라오는 것이었다. 유튜브 약관 확인 결과 그 형태가 불가능해서 폐기했다. 확인된 조항은 셋이다.
  • 플레이어 최소 크기 — Required Minimum Functionality: "Embedded players must have a viewport that is at least 200px by 200px." 16:9로 높이 200px을 맞추면 너비가 356px이다. 375px 폰에서 화면을 꽉 채우므로 "미니"가 성립하지 않는다.
  • 오디오 분리 금지 — Developer Policies III.I: "separate, isolate, or modify the audio or video components". 축소하면서 영상을 숨기고 소리만 남기는 것이 금지된다.
  • 오버레이 금지 — RMF: "must not display overlays, frames, or other visual elements in front of any part of a YouTube embedded player". 플레이어 위에 곡 제목이나 닫기 버튼을 덮을 수 없다. 옆이나 아래는 된다.
참고로 background player 금지 조항에는 걸리지 않았다 — 그 정의가 "사용자가 보는 화면에 표시되지 않는 플레이어"라서, 보이는 미니 플레이어는 해당이 안 된다. 죽인 것은 크기 규정이다. 또한 API 키 없이 순수 <iframe>만 써도 Developer Policies와 RMF가 적용되고, 무료·비상업 예외는 없다.

그래서 재생을 ⑥ 곡 상세로 옮겼다. 플레이어를 상단에 고정하고 기억만 스크롤시키면 플레이어가 항상 200px 이상으로 화면에 보이므로 세 조항을 전부 통과한다. 그리고 노래가 흐르는 동안 남의 기억을 읽어 내려간다는 원래 목적은 그대로다.

  • 피드에 iframe을 하나도 깔지 않으므로 피드가 훨씬 가볍다. iframe 하나가 수 MB다.
  • "한 페이지에 자동 재생 플레이어는 하나만"이라는 RMF 규정이 자동으로 지켜진다.
  • 자동 재생은 "플레이어의 절반 이상이 보이기 전에는 시작할 수 없다". 상단 고정이므로 조건을 충족한다. 다만 모바일 브라우저의 소리 자동재생 차단은 별개라 첫 재생은 사용자가 눌러야 한다. 요확인
  • 잃는 것 — 피드를 훑으며 음악을 듣는 경험은 없다. 들으려면 카드를 탭해 들어가야 한다.

배치에 담긴 결정

  • ①에 계정·약관·권한이 없다. 서버는 기기 비밀키의 해시만 갖는다. 수집하는 개인정보가 0건이라 물어볼 게 없다.
  • ②는 그 곡의 첫 사람만 본다. 두 번째 사람부터는 영상이 이미 정해져 있어 이 화면을 건너뛴다. 유튜브 검색 호출이 사용자 수가 아니라 곡 수에 비례하게 되는 지점.
  • ③의 칩은 전부 사람으로 시작한다. "이 노래는" 같은 칩을 일부러 뺐다 — 그쪽으로 새면 기억이 아니라 곡 감상평이 된다.
  • ③의 라벨은 전부 선택 사항이고 올리기 버튼 바로 위에 있다. 안 고르고 눌러도 아무 일 없다. 계절 라벨이 쌓이면 겨울에 겨울 글을 먼저 보여줄 수 있다 — 푸시도 스트릭도 없이 돌아올 이유가 된다.
  • ⑤에 좋아요 숫자가 없다. ♡만 있고 개수는 안 보인다. 누군가의 진심이 "♡ 0"으로 박히면 안 되기 때문. 개수는 DB에만 있고 정렬에만 쓴다.
  • ⑤에 싫어요가 없다. 기억에는 틀린 게 없다.
  • 카드의 "나도 적기"가 ③으로 돌아가는 두 번째 입구다. 온보딩에서 "다음에 적을게요"로 빠져나간 사람이 남의 글을 읽다 여기서 잡힌다.
  • ⑤의 정렬 기본값은 "지금 계절"이다. 9월이면 가을 글이 위로 온다. 겨울이 오면 홈이 저절로 바뀐다 — 푸시도 스트릭도 없이 계절이 사람을 부른다. "오래 남은"은 좋아요 순인데, 숫자를 안 보여주기로 했으니 이름에서도 숫자 냄새를 뺐다.
  • ⑦이 사람 아이콘이 아니라 갈피인 이유. 로그인이 없는 제품에서 프로필 자리에 사람이 앉아 있으면 "로그인해야 하나" 싶어진다. 갈피는 서비스 이름과 같은 은유라, 이름·아이콘·기능이 한 줄로 이어진다.
  • ⑥은 v1에서 noindex. "밤편지 가사 의미"로 검색해 들어온 사람이 글 3편을 보면 유튜브 수만 개와 바로 비교된다. 곡당 평균 5편을 넘으면 그때 열기로 기준을 숫자로 박아뒀다.

모더레이션 — 대기열을 만들지 않는다

"걸린 글은 운영자가 확인"으로 설계하면 매일 대기열을 봐야 하는 제품이 된다. 하루만 안 봐도 사람들 글이 멈춘다. 그래서 자동 필터를 좁은 그물로 만들고, pending 상태를 아예 두지 않는다.
  • 즉시 돌려줌 — 전화번호·계좌·실명+소속 같은 명백한 개인정보. "이 부분은 빼주세요"로 고칠 기회를 준다.
  • 즉시 거절 — 노골적 유해물.
  • 그냥 통과 — 애매한 것 전부. 문제가 되면 신고로 잡힌다.
그래서 status는 visible / hidden / removed 셋이면 끝난다. 운영자는 신고가 들어온 것만 보고, 그건 Vercel 대시보드의 Data editor에서 행을 직접 지우면 된다 — 어드민 화면을 만들 필요가 없다.

이 그림이 아직 안 정한 것

③에서 자동 필터에 걸렸을 때의 화면. "이 부분은 빼주세요"를 어떤 톤으로 보여줄지. 여기서 기분이 상하면 그 사람은 안 돌아온다.
글이 0개일 때의 ⑤. 시드는 Tabber가 곡 8~10개 · 기억 12~15편을 직접 적는다. 시드는 콘텐츠가 아니라 규범이다 — 사람들은 앞사람 글을 보고 자기 글의 길이와 톤을 맞춘다. 운영자 표시는 달지 않는다.
②를 v1에 넣을지. 일곱 화면 중 유일하게 무겁다(유튜브 검색 → 후보 렌더 → 직접 링크 → 검증). 다만 빼면 첫 사람이 모바일에서 유튜브 앱을 오가며 링크를 복사해와야 한다 — 새 곡이 안 쌓일 위험.
남은 미확인. 모바일 자동재생 정책 실측 · Neon 콜드스타트 실측 · 개인정보처리방침 필요 여부.

확인 끝난 것 (2026-09-16)

  • 유튜브 임베드 약관 — 표준 IFrame 임베드는 허용. 미니 플레이어만 불가(위 참조). 제재 사례는 전부 광고 우회·비공식 플레이어(Musi·Invidious·Vanced)였고, 표준 임베드 서비스는 생존 중(Watch2Gether).
  • YouTube Data API 쿼터 — 2026-06-01에 모델이 바뀌었다. search.list가 전용 버킷으로 분리되어 하루 100 calls가 경성 상한이다. 다른 호출을 아껴도 늘릴 수 없다. 즉 신규 곡 하루 100개. 반면 videos.list는 공용 10,000 units 풀이라 캐시된 곡 조회는 사실상 무제한 — 곡당 1회만 검색하는 설계가 정확했다.
  • API 키 발급 장벽 없음 — 감사(audit)는 기본 할당량 초과 요청 시에만 요구된다. GCP 프로젝트 + 키로 즉시 시작. 단 90일 연속 미사용 시 접근이 차단될 수 있다(Developer Policies III.D.4) — 직접 링크 폴백을 항상 열어둘 이유.
  • 곡 검색·메타데이터 — iTunes Search API(media=music, country=us), 무인증. 한국어 질의 정확. entity=song+country=kr 조합만 항상 0을 반환하는 함정이 있다.
  • DB — Neon Postgres. 리포에 이미 있다([CodeStudy/Backend]). 무료 0.5GB, 5분 비활성 시 자동 정지. 그래서 피드 첫 페이지는 60초 캐시로 DB를 안 건드리게 한다.
