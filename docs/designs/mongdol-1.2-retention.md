## Problem Statement

몽돌 1.1.1 이 출시됐고 한글날(10/9) 인스타 광고로 새 사용자가 들어오기 시작했다(PostHog 기준 10/8~9 기기 8대). 1.2 는 「새로 깐 사람이 다음 날 다시 여는가(D1)」를 올리는 버전으로 잡는다. 원칙은 그대로다: 매일 밤 하루를 덮는 앱이 아니다, 연속 기록·재촉 알림 금지, 사진은 기기 밖으로 나가지 않는다.

## Demand Evidence

결제한 사람은 없다. 행동 근거는 PostHog 8명(대시보드 1010601·1010644·1010653)과 외부 피드백 2건뿐이고, 표본이 작아 「신호」로만 쓴다.

- 온보딩 이탈은 0명(8/8 끝냄). 첫 사진도 온보딩 안(firstPebble 화면, 사진 앱에서 고르기)에서 7/8 이 담는다 — **첫 행동은 이미 일어난다.**
- 그런데 온보딩을 끝내고 중앙값 **0.7분** 뒤 앱을 나간다(5명). 설치한 날 다시 연 사람은 3/8.
- 카메라를 연 14번 중 7번은 10분 안에 아무것도 담지 않았다(여는 길과 무관하게 50%). 10/9 들어온 6명 중 몽돌 카메라로 직접 찍은 사람은 0명 — 다만 모두 밤 9시 이후 설치.
- 외부 피드백(2026-10-07): 「그라데이션이 제대로 안 되는 것 같다」, 「한 사진에서 색 여러 개 뽑아 주는 줄 알았다」.
- 코드 사실: 사진 한 장에서 색을 **하나만** 뽑는다(`ColorExtractor.symbolicColor` → `histogramColors(count: 1)`). 그래서 사진 1~2장인 날의 조약돌은 단색에 가깝고, 새 사용자의 첫 조약돌이 대부분 이 경우다.

## Status Quo

사람들은 기본 카메라로 찍고 사진 앱에 쌓아 둔다. 몽돌의 경쟁자는 다른 기록 앱이 아니라 「사진 앱에 그냥 두기」다(Tabber 동의, 근거는 10/8~9 첫 사진 6/7 이 사진 앱에서 담김 — 단 온보딩이 사진 앱 고르기를 안내하므로 이 수치 자체는 약한 근거).

이미 있는 것: 홈 맨 위 「카메라 앱으로 찍은 사진 N장 · 눌러서 몽돌에 담기」 카드(`HomeView.cameraAppCard`). 이 카드로 담은 사진은 `Photo.added(source: library)` 로 찍혀 사진 앱 목록에서 직접 고른 것과 **구분되지 않고**, 카드가 보였는지도 기록되지 않는다.

## Target User & Narrowest Wedge

- 사람: 「순간을 남기고 싶을 때 쓰고, 남겼다면 소소한 수집도 가능한」 사람(포지션 원문). 이름으로 특정된 사람은 아직 없다 — 아래 Assignment 에서 처음 만난다.
- 쐐기: **설치 다음 날 아침 한 번.** 업계 공식(첫 세션 행동 → D1 2~3배)은 보상이 즉시 온다는 전제다. 몽돌의 보상은 다음 날 아침에 오고, 첫 행동은 이미 하고 있다. 그래서 1.2 는 온보딩에 할 일을 더하지 않고 **아침에 도착하는 첫 조약돌을 진하게** 한다.

## Constraints

- 연속 기록·재촉 알림 금지(SPEC §2-4). 도착 알림은 「보상 도착」이라 허용 범위 — 참고 숫자(블로그 인용, 1차 출처 미확인): 주 1~3회 받은 사용자는 90일 리텐션 +34%, 주 6회 초과는 −21%([Chop Dawg](https://www.chopdawg.com/the-app-retention-playbook-streaks-habits-and-notifications-that-keep-users/)). **1.2 는 도착 알림을 바꾸지 않는다** — 알림이 사람을 데려오는지 먼저 `App.entered` 로 잰다.
- 홈에 버튼을 늘리지 않는다(DESIGN §1.2).
- 사진은 기기 밖으로 나가지 않는다. 팔레트(색 hex)는 기록·사용자 iCloud 에만 — 사용 기록(PostHog)에는 색을 보내지 않는다.
- 그라데이션은 실기기에서 두 번 기각된 자리 — 그리는 규칙은 실기기 시안으로 정한다.
- 이미 받은 조약돌의 색은 바뀌지 않는다(받은 조약돌은 도장).

## Premises (합의, 2026-10-09)

1. 몽돌의 경쟁자는 「사진 앱에 그냥 쌓아 두기」다.
2. 첫 행동(첫 사진)은 이미 온보딩 안에서 일어난다. D1 을 가르는 건 「다음 날 아침 도착」(알림 + 첫 조약돌의 질)이다.
3. A(사진 한 장인 날의 조약돌)는 1.2 에 넣는다. 단 착수 전 친구 2명을 옆에서 지켜봐 「조약돌에 실망」인지 「조약돌이 뭔지 모름」인지 확인한다.
4. 오늘 카드·도착 알림·조약돌 보기가 기록되지 않으면 A 의 효과를 잴 수 없다 → 계측은 A 와 같은 1.2 묶음이다. **단 기준선을 얻으려고 계측을 먼저(1.1.2) 내고, 팔레트는 1.2.0 으로 뒤따른다**(spec review R1-1 반영, Tabber 승인 때 확인).
5. 2주차 이후 돌아올 이유(쌓임 — 조약돌 이름 필터 C)는 1.3 이다. 「기다렸다 받기」는 신선함이 닳는다(Dispo).

## Approaches Considered

- **1 적은 날만 새로 칠하기** — 1~2장 날만 하루가 닫힐 때 사진을 다시 읽어 색 2~4개로 칠한다. 가장 빠르지만 닫힐 때 원본을 다시 읽어야 해 iCloud 에만 있는 사진이면 깨지고, 1.3 에 남는 게 없다.
- **2 사진마다 색 팔레트 저장 — 채택.** 아래.
- **3 색 대신 기대를 고치기** — 「사진이 많을수록 색이 섞여요」 한 줄 + 저녁 오늘 카드. 반나절이면 끝나지만 외부 피드백 2건을 풀지 못한다. **관찰 결과가 「조약돌이 뭔지 몰랐다」면 이 안으로 바꾼다.**
- 기각: B(오늘 찍은 사진 담기)를 새로 만들기 — 이미 `cameraAppCard` 로 있다(Tabber 지적). C(이름 필터)를 1.2 로 — 조약돌이 5개씩 쌓여야 의미가 있어 지금 사용자 대부분이 못 본다.

### 2-1. 담는 순간 팔레트 저장

- 사진을 담는 세 길(몽돌 카메라 `CaptureEngine`, 잠금화면 `CaptureInbox`, 사진 앱 `LibraryImporter`/오늘 카드) 모두 지금 대표 색을 뽑는 그 자리에서 — 잠금화면도 확장이 아니라 앱 본체가 넘겨받을 때(`CaptureInbox.swift:165`, 앱 타깃) 색을 뽑으므로 확장 메모리 제한과 무관 — `histogramColors(count: 4)` 로 주요 색 3~4개와 비중을 함께 뽑아 `Moment` 에 저장한다(새 선택 필드, 예: `palette: [PaletteColor]?`, hex + 비중). 대표 색(`color`)은 지금 값 그대로 둔다 — 홈 블록·타임라인은 계속 대표 색을 쓴다.
- **2026-10-10 발견 — `histogramColors(count: 4)` 를 그대로 쓰면 안 된다.** 고른 색의 이웃 빈(픽셀은 없고 점수만 있는 빈)이 다시 후보가 되어 거의 같은 색을 네 번 고른다(시안 페이지에서 확인: 주황 #E9B07D·#E6AB7A·#E9AE7C·#EDB883). 팔레트용으로는 「이미 고른 색에서 축마다 2칸 안의 후보는 건너뛴다」를 더한 새 함수를 쓴다. 첫 색은 지금 `symbolicColor` 와 같게 남아 대표 색은 바뀌지 않는다. 비중 = 고른 색 이웃 픽셀 가중치 합 ÷ 전체, 비슷한 색(RGB 거리 0.10 미만)은 합치고 8% 미만은 그리기에 쓰지 않는다.
- **1.1.2: 기존 사진 채우기(아래)는 빼고 다음 버전으로**(Tabber 결정 2026-10-10). 새로 담는 사진부터 팔레트를 저장한다.
- iCloud: `Moment` 레코드에 선택 필드 `palette`(hex 문자열 배열, 비중 순)를 더한다.
  - **구버전이 지우지 않는다**: 저장할 레코드는 `SystemFieldsCache` 의 시스템 필드만 든 빈 `CKRecord` 에 `SyncRecords.fill` 이 아는 키만 채워 만든다(`CloudSync.swift:93`). 구버전은 `palette` 키를 아예 보내지 않으므로 서버 값이 남는다. 이걸 테스트로 못 박는다 — 「새 버전이 palette 를 쓴 레코드 → 구버전 fill 로 다시 저장할 레코드를 만들었을 때 palette 키가 없다(=보내지 않는다)」.
  - 구버전은 모르는 키를 읽지 않는다(`moment(from:)` 가 아는 키만 읽음).
- 기존 사진 채우기(팔레트 없음) — 원본이 있는 곳별로:
  - 사진 앱 사진(`library`, 그리고 사진 앱에 입양된 `app`·`locked`): `assetID` 가 있는 기기에서 `PHAsset` 을 작은 크기로 읽어 뽑는다. iCloud 에만 있는 원본은 네트워크로 받지 않는다(`isNetworkAccessAllowed = false`) — 못 읽으면 건너뛴다.
  - 입양 전 앱 안 파일만 있는 사진: `ShotStore` 파일에서 뽑는다.
  - 다른 기기에서 받은 기록(`assetID` 없음): 채우지 않는다. 원래 기기가 채워 올린 `palette` 를 받는다.
  - 예산: 앱이 앞에 있을 때 한 번에 최대 30장, 하루 최대 200장. 아직 받지 않은 날 → 최근 받은 날 순(받은 날은 도장이라 그림은 안 바뀌지만, 1.3 이름 필터의 재료로 채운다). iCloud 저장은 지금 동기화 묶음 그대로 모아 보낸다.
  - 같은 사진을 두 기기가 채워도 같은 원본·같은 함수라 결과가 같다(결정적). 마지막 저장이 이겨도 값이 같다.

### 2-2. 조약돌 그리기

- 장수와 관계없이 조약돌의 색 정지점을 「사진들의 팔레트를 비중대로 섞은 것」에서 고른다. 사진이 많은 날은 사진마다 대표 색 위주(지금과 비슷), 1~2장인 날은 그 사진의 팔레트가 정지점을 채운다.
- 정확한 규칙(정지점 수, 비중 하한, 비슷한 색 합치기)은 **실기기 시안 2~3개를 Tabber 가 보고** 정한다. Tabber 의 실제 1~2장 날 기록으로 전후를 나란히 본다.
- **2026-10-10 결정 — 규칙 B「대표 + 곁들임」**(시안 페이지 https://claude.ai/artifact/VrnoaRi7SYMiH49nu44Ncz 에서 Tabber 선택). 사진마다 자기 몫 구간(사진 i 는 [i/n, (i+1)/n])을 갖고, 그 안을 대표 색 60% + 나머지 주요 색(비중 8% 이상, 최대 2개)이 40% 를 똑같이 나눈다. 곁들일 색이 없으면 대표 색 100%. 정지점은 각 몫의 가운데. 팔레트가 없는 사진(구버전·다른 기기 기록)은 대표 색 100% 몫.
- **받은 조약돌은 도장**: 받는 순간의 색 정지점(hex + 위치)을 그날 `Day` 레코드의 선택 필드 `pebbleStops` 로 저장하고 iCloud 로 나눈다(`gifted`·`pebbleName` 과 같은 레코드). 어느 기기든 `pebbleStops` 가 있는 날은 그것으로만 그린다. 구버전은 이 키를 보내지 않으므로 지우지 않는다(위와 같은 이유).
- **도장 없는 받은 날은 언제나 1.1 규칙으로 도장**: 첫 실행 한 번이 아니라 계속 지키는 규칙이다. 1.2 기기가 `gifted` 인데 `pebbleStops` 가 없는 날을 보면(로컬에 있던 날이든, 1.1.x 기기가 나중에 받은 날이 iCloud 로 들어온 것이든, 새 기기에서 첫 동기화가 늦게 끝나 들어온 것이든) **1.1 규칙**(`DayGradient.pebbleStops`)으로 그린다. 도장 **저장**은 그날 사진 기록이 다 모였다고 볼 수 있을 때만 — 동기화 받기가 남은 변경 없이 끝난 뒤(첫 동기화 완료 포함). 그 전에는 1.1 규칙으로 그리기만 하고 저장하지 않는다(R3-1). 새 규칙으로 도장을 찍는 건 그 1.2 기기가 직접 증정한 날뿐이다. 다른 기기에서 이미 도장이 왔으면 덮지 않는다. 테스트: ① 받은 날의 그림이 1.2 업데이트 전후 같다 ② 첫 실행 뒤에 도장 없이 동기화로 들어온 받은 날도 1.1 과 같게 그려진다 ③ `gifted` 날 레코드가 그날 사진 기록 일부보다 먼저 와도, 최종 도장은 사진이 다 모인 뒤 1.1 규칙 결과와 같다.
- 섞인 버전 기간: 1.2 기기가 새 규칙으로 증정한 날은 같은 iCloud 의 1.1.x 기기에서 1.1 규칙으로 보인다(구버전은 `pebbleStops` 를 모른다). 업데이트 전까지 기기마다 색이 다를 수 있음을 받아들인다(R3-6).
- 홈 블록·타임라인은 계속 대표 색 하나를 쓴다 — 1~2장 날은 홈과 조약돌의 색 느낌이 다를 수 있다. 의도한 차이(조약돌은 「빚어진 것」)로 두되, 실기기 시안에 홈과 조약돌을 나란히 넣어 Tabber 가 본다.

### R3-1 — completeness (blocking)

**Problem**

> The new continuous rule stamps an unstamped gifted day with the 1.1 rule as soon as a 1.2 device sees it, 'before rendering', including days arriving during a late first sync. The 1.1 rule is computed from that day's Moment records, but the Day record (gifted) can arrive before all of that day's Moment records have synced. The 1.2 device would then compute stops from an incomplete photo set, persist them as a permanent stamp, and push it via iCloud; because other devices never overwrite an existing stamp, every 1.2 device freezes a color that differs from what the gifting 1.1 device showed. This breaks the Constraint/Success Criterion that a received pebble's color never changes, and test ② does not cover partial-sync ordering.

**Remedy**

> Only persist a 1.1-rule stamp once the day's moments are known to be complete (e.g., after a sync fetch drains with no more pending changes / initial sync finished); until then render with the 1.1 rule live without saving. Add a test where the gifted Day record arrives before some of its Moment records and the final stamp equals the 1.1 rendering over the full set.
